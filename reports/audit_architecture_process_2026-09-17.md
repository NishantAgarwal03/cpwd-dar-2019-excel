# Architecture/Process Audit — Can raw_pdf/ be deleted?

Scope: process/architecture only (no numeric spot-checking; that is covered by a separate audit).

## (a) Pipeline steps: PDF-direct vs. unverified-intermediate

| Step | Script | Actual primary input (verified by reading code) | PDF touched? |
|---|---|---|---|
| 1 | `extract_rates.py` | **Converted XLSX is primary** (`VOL1_CONVERTED_XLSX`, sheet `00_Basic_Rates`, lines 41-75 build the full item list). PDF (`pypdf.PdfReader`, lines 8-36) is parsed only to **gap-fill** rates where the XLSX cell is blank (line 80: `if it['rate'] is None and it['code'] in pdf_rates`). | Yes, but only as a fallback for missing cells — not as the source of truth for the ~majority of rows. |
| 2 | `extract_norms.py` | `VOL1_CONVERTED_XLSX` only (line 6: `openpyxl.load_workbook(VOL1_CONVERTED_XLSX, ...)`). | **No** — never imports pypdf/pdfplumber, never references `PDF_CIVIL_DAR_VOL1`. |
| 3 | `vol1_chapter_extractor.py` | `VOL1_CONVERTED_XLSX` only. Its own docstring (lines 1-8) states: *"Extract Ch.03–12 resource rows from CivilDAR_2019_Vol_1_Converted.xlsx"* and *"Converted XLSX → ch0N_items.json"*. | **No** — no pypdf/pdfplumber import at all. |

| 5 | `cpwd_item_parser.py` | `support_builder_earth_v2.ITEMS` (hand-typed Python list, ch02) + `ch03-12_items.json` (from step 3, i.e. also ultimately XLSX-derived). | No. |

| 8 | `generate_vol2_workbook.py` | Reads only `ch13-26_items.json` outputs; no PDF/XLSX references found. | No. |

**Bottom line:** Of the two chapter-extraction scripts that matter most for Vol 1 (which covers Ch 02-12, the bulk of the dataset), **neither reads the PDF**. `vol1_chapter_extractor.py` (Ch03-12) and `extract_norms.py` (labour/sundries norms) are 100% dependent on `data/converted_xlsx/CivilDAR_2019_Vol_1_Converted.xlsx`. `extract_rates.py` is majority-XLSX with the PDF used only as a blank-cell patch. Only Vol 2 (Ch13-26, via `vol2_chapter_extractor.py`) and Ch02 (`support_builder_earth_v2.py`, see below) have a real claim to being PDF-derived — and even Ch02 is hand-typed, not extracted.

## (b) Provenance of the converted XLSX files

- `git log --all --oneline -- "data/converted_xlsx/*"` shows only 2 commits: `ccafa37` (initial add) and `6e8cb52` ("refactor: organize repo... optimize git storage" — a *move*, not a creation). **No commit shows these files being generated by any script in this repo.**
- No script anywhere under `scripts/` writes to `CivilDAR_2019_Vol_1_Converted.xlsx` or `..._Vol_2_Converted.xlsx` — they are only ever *read* (`openpyxl.load_workbook`). There is no PDF→XLSX converter script in the codebase.
- Conclusion: these two files were produced **outside this repository** (manually re-typed, or via some external/manual PDF-to-Excel conversion tool), and **their fidelity to the source PDFs has never been checked by anything in this repo.** Three of the eight pipeline steps (1 partially, 2, 3 fully) trust these files unconditionally. This is the single biggest hole in the "single source of truth" claim.

## (c) run_pipeline.py correctness

- `run_pipeline.py` (lines 76-85) does correctly sequence steps 1→8 in the order PIPELINE.md documents, and each step's own module is idempotent (overwrites its output file).
- However, it **omits Ch02 and the Ch03-12 "teaching sheet" support_builder scripts entirely** — `support_builder_earth_v2.py`'s `ITEMS` list is consumed by step 5 (`cpwd_item_parser.py`, confirmed import at line 29 of that file: `import scripts.support_builder_earth_v2 as _earth_v2`), so Ch02 registry data is regenerated correctly. But `support_builder_mortars.py`, `_concrete.py`, `_rcc.py`, `_masonry.py`, `_stone.py`, `_cladding.py`, `_wood_pvc.py`, `_steel.py`, `_flooring.py`, `_roofing.py` (the Ch03-12 teaching-sheet scripts) are **not called by `run_pipeline.py`, `main.py`, or any other orchestrator** — grep across the whole repo shows no importer of any of them except their own file. They must be run manually and standalone, writing directly into a workbook file. `python run_pipeline.py` will **not** regenerate whatever teaching-sheet content currently sits in the delivered workbook for Ch03-12 — that content is one-off and can silently go stale relative to `ch03-12_items.json` even after a full pipeline run.
- `scripts/paths.py`'s `resolve_path()` (lines 26-45) is a real stale-fallback risk: if a canonical file under `data/<subfolder>/` is missing, it silently falls back to checking the project root, then `data/`, before finally defaulting to a path that may not exist. If an old copy of e.g. `rates_master_clean.json` happens to sit in the project root (from before the "organize repo into structured data directories" refactor, commit `6e8cb52`), it would be picked up silently instead of raising an error. This wasn't observed to be currently happening (the "files to delete" list — see (e) — is already gone), but the fallback logic itself is a latent risk for any future partial run.

## (d) Single-source-of-truth violations / duplication

- Confirmed per PIPELINE.md's own admission: `support_builder_mortars.py` (and the 9 sibling Ch03-12 scripts) contain fully hand-typed item data (e.g. `MORTAR_ITEMS` list, `support_builder_mortars.py` lines 36+) that duplicates — but is never cross-validated against — `ch03_items.json`...`ch12_items.json`. No script in the repo diffs or reconciles the two. This is a live divergence risk (matches the known open gap noted in project memory: mortar item 3.19).
- `support_builder_earth_v2.py`'s `ITEMS` (Ch02, ~2000+ lines, hand-typed rates/gangs/materials, e.g. lines 74-172) has no extraction script behind it at all — it is pure hand-entry. It also pulls item *descriptions* from `data/reference_json/earthwork_pdf_specs.json` (line 34-39), but **no script in the repo generates that JSON file either** (git log shows it was added whole in commit `ccafa37`, no generator found) — its own fidelity to the PDF is equally unverifiable in-repo.
- `cpwd_item_parser.py` / `cpwd_item_parser_vol2.py` (registries) do trace cleanly back to the JSON files (steps 3/4 outputs) with no extra hand-typed duplication — this part of the chain is sound, *conditional on* the JSONs themselves being correct (which for Ch02/Ch03-12 ultimately depends on the unverified converted XLSX / hand-typed ITEMS, per (a)/(b)).

## (e) Stale/superseded files

All 12 files PIPELINE.md lists under "Files to delete (pending explicit user confirmation)" are **already gone** from the working tree (confirmed via direct filesystem check) — consistent with the recent commit `933a851 chore: remove 12 superseded files`. No dangling references to any of them were found. This section of PIPELINE.md is now stale documentation (describes a cleanup already completed) but poses no risk itself.

## (f) Verdict: is it safe to delete the raw PDFs?

**No — not yet, and not without additional work.** The architecture does not actually support the claim that the extracted JSON/workbook data is independently verified against the PDFs:

1. The two converted XLSX files (`CivilDAR_2019_Vol_1/2_Converted.xlsx`) are the **real primary source** for Ch02 descriptions, Ch03-12 items, and labour/sundries norms (Vol 1 covers the majority of the dataset) — and these XLSX files have **no traceable, in-repo provenance or fidelity check against the PDF**. They could contain manual transcription errors that would propagate silently through steps 1-3, 5, and 7 undetected, because nothing in the pipeline compares JSON output back to PDF text.
2. `extract_rates.py`'s PDF read is only a gap-filler, not a primary or comparison source — it cannot catch errors in cells the XLSX did populate.
3. Ch02 (`support_builder_earth_v2.py`) and the Ch03-12 teaching sheets (`support_builder_*.py`) are hand-typed data with **no automated reconciliation** against the canonical JSONs, and the teaching-sheet scripts aren't even wired into `run_pipeline.py` — so the delivered workbook's teaching content can diverge from the "canonical" JSON without any pipeline run detecting it.
4. Only Vol 2 (Ch13-26) has a clean, automated, PDF-direct extraction path (`vol2_chapter_extractor.py` via pdfplumber) with no unverified intermediate.

**What would need to be true before the PDFs could safely be deleted:**
- An automated, in-repo script that parses each PDF directly (like `vol2_chapter_extractor.py` already does) and diffs its output against the converted XLSX / ch0N_items.json for Ch02-12, with all discrepancies resolved.
- The converted XLSX files' provenance documented (how were they made, by whom/what tool) or replaced entirely by direct PDF extraction, eliminating dependency on an unauditable intermediate.
- The Ch03-12 `support_builder_*.py` teaching sheets either wired into `run_pipeline.py` with a JSON-diff check, or regenerated from the JSONs programmatically instead of hand-typed.
- Ch02's `ITEMS` list and `earthwork_pdf_specs.json` given a traceable generation/verification path back to the PDF.

Until these are addressed, the PDFs remain the only artifact that can be used to actually verify — as opposed to merely assume — that the extracted data is correct. Numeric-accuracy spot checks by other agents cannot substitute for this: 100% cell-level agreement today does not guarantee the *pipeline* would still reproduce correct data on any future rebuild, since large parts of it depend on files no one in this repo can regenerate or audit.
